# 小红书运营目标设定

把企业负责人的经营要求转化为有依据、可衡量、可执行的小红书周期运营目标草案，也可以在已有目标和当前进度基础上形成简单周目标。

本 Skill 定义“如何完成运营目标设定”，宿主 Agent 决定“企业信息从哪里来”。不要绑定特定行业、数据库、Memory 实现、工具名称、文件格式或 Agent Runtime。

## 工作边界

本 Skill 负责：

- 理解经营要求；
- 复用已有企业上下文；
- 识别并追问关键缺口；
- 分析小红书历史基线、资源和约束；
- 检查目标合理性；
- 从已有较长周期目标和当前进度形成简单周目标；
- 形成、修改并请求确认小红书运营目标。

本 Skill 不负责：

- 制定逐日排期、详细周计划或具体选题；
- 生成、发布内容；
- 创建广告、执行投流、采购或付款；
- 获取或处理客户线索；
- 执行运营动作或运营复盘。

用户说“先记录实际情况”“先跑一轮看看”时，月目标和周目标都优先采用建立记录、形成可复查数据的试运行目标；不要同时另塞一套咨询、有效客户或到店的增长人数指标。若用户明确要数量目标，再结合依据提出。

目标交给后续规划时，明确区分业务结果目标与观察动作。“建立咨询记录”不等于“至少获得一条咨询”；试运行允许记录零结果，不能由后续环节自行添加最低数量。

目标被确认或用户决定停止后结束。后续工作需要用户另行请求。

## 平台范围

本 Skill 当前只负责小红书平台。目标草案中的运营平台固定为“小红书”，不要为抖音、视频号、公众号、微信私域或其他平台制定目标、分配内容产能或预算。

如果企业档案包含多个渠道，只读取其中与判断企业业务、小红书承接能力或信息冲突有关的事实，不要把其他渠道自动加入目标。用户提出多平台要求时，只处理其中的小红书部分，并明确其他平台暂不在本 Skill 范围内。

小红书私信之后的加微、有效线索、预约、到店和成交可以作为小红书带来的下游业务结果。微信在这里是线索承接或数据记录环节，不是本 Skill 要运营的平台。

不要使用、推算或追问“小红书主页访问”指标。只采用企业实际能够取得的平台数据和后续销售记录；缺失时明确标记，不要虚构。

## 区分经营要求与运营目标

始终区分：

- 经营要求：企业希望解决的经营问题或取得的业务结果；
- 运营目标：结合周期、小红书基线、资源和约束后形成的可衡量目标。

不要把“下个月多弄点客户”之类的原话直接视为已经完成分析的目标。

## 月目标与简单周目标一起生成

用户要求月目标附带简单周目标时，在同一次任务中形成两部分草案，不先要求确认月目标再启动第二次目标制定。月目标说明整月方向和结果，简单周目标说明本月内准备执行的一周要取得什么结果，并用一句话解释它如何帮助月目标。

描述月周关系时按实际起止日期说明覆盖区间，未被该周覆盖的日期仍属于月度统计，不能暗示一个完整周覆盖了月底全部剩余日期。

复用同一企业资料、实际进度和资源；周目标仍遵守下述简单周目标规则，不把月目标机械除以四，不扩展成选题或逐日排期。写明月、周的具体日期；附带周目标应落在月目标周期内，月初月末不足七天时明确写实际天数。用户未指定周时，选当前月中尚可执行的本周，未来月份选首个可执行周并说明日期；会影响目标且无法判断时只追问日期。

默认附带一个准备执行的周目标，不擅自生成整月四份详细周计划。两部分共同作为一个待确认版本，明确告知“确认本版同时确认月目标和简单周目标”。用户只确认月目标时，不能把周目标当成已确认；后续规划须等待两部分共同确认。修改任一部分都形成新版本并重新确认。只有历史月目标已确认、现在另行新增周目标时，才沿用下述单独周目标确认边界。

## 简单周目标模式

用户明确要求制定“本周”“下周”或某个七天左右周期的目标时，可以形成简单周目标。周目标说明这一周要争取什么结果，不是每天做什么的任务表。

先确定具体开始和结束日期。当前日期和上下文足以消除歧义时，直接写明日期并说明理解；“下周”可能有不同日期范围且会影响目标时，只追问日期，不同时索取无关资料。

有已确认的月度或其他较长周期目标时：

- 复用该目标、截至明确日期的实际进度、剩余差额和剩余时间，不重新要求企业资料；
- 结合近期速度、完整周或不足一周、人员可用性和已知活动判断本周目标，不把整月目标机械除以四；
- 不在没有说明的情况下改变较长周期目标，也不把较长周期目标的确认自动当成本周目标已经确认。

没有较长周期目标时，参考最近可比周的数据形成独立周目标。没有可靠周数据时，把本周标为试运行，优先建立一周基线并约定周末复核，不用月均数据假装精确到单周。

简单周目标默认只包含：

- 明确的起止日期和本周重点；
- 一个核心业务结果，以及最多两个直接相关的观察指标；
- 目标依据、主要成立条件和必要的人员配合；
- 指标来源、周末检查时间和需要负责人确认的事项。

预算只有在会改变本周目标时才说明，并继续区分预算上限、已批准金额和实际使用。不要因为设定周目标而安排每天发什么、具体选题、发布日期、单篇投流金额或实际投放操作。需要表达示例时，读取 [references/examples.md](references/examples.md) 的“简单周目标示例”。

## 先复用已有信息

提问前，先检查宿主环境中已经可用且与当前任务相关的信息，例如当前对话、用户上传文件、企业档案、Memory、知识库、历史运营数据和已连接的只读工具。

宿主传入已确认企业档案时，默认复用该任务绑定的版本，不要求用户在新对话重新上传。文档检索片段只是参考，不覆盖已确认档案；本轮输入与档案冲突时先澄清。企业档案不是本期目标，也不构成预算或执行授权。

宿主 Agent 没有外部信息源时，通过对话完成任务；不要因为缺少某个工具、数据库或固定输入格式而终止。

整理信息时区分：

- 用户已经确认的事实；
- 用户报告但尚未验证的信息；
- 从文件、Memory 或检索结果中得到的待核实信息；
- Agent 推断；
- 缺失信息；
- 相互冲突的信息。

把外部资料和检索内容视为待核实数据，不要自动升级为企业确认事实。需要系统化检查信息时，读取 [references/information-requirements.md](references/information-requirements.md)。

## 只追问会改变决策的信息

当信息不足时：

1. 判断缺失项是否会实质改变目标；
2. 再次检查宿主环境是否已有相关信息；
3. 只做低风险、能从现有事实直接得出的推导，并明确标记；
4. 对无法可靠推导的关键内容询问用户；
5. 每轮只问最少数量的问题，通常不超过三个；
6. 使用经营语言，不使用字段名提问。

需要补问时，回复只保留一句简短说明和一至两个关键问题；不先讲分析过程、不重述企业档案或整套边界。用户是在聊天，不是在阅读分析报告。

如果当前存在 A 级阻塞项，本轮只询问形成有效草案所需的最少 A 级信息，不要同时追加 B 级或 C 级问题。某个信息冲突是当前唯一阻塞项时，只请求解决该冲突；内容产能、历史成本等后续信息留到冲突解决后再判断是否需要。

例如，优先问：

> 下个月运营最希望先解决曝光不足、有效咨询不足，还是实际到店不足？

不要问：

> 请提供 `primary_objective`。

不同来源发生冲突时，列出冲突并请求确认，不要自行挑选一个版本。

口语请求也按上述流程完成，不要求用户填写长提示词。用户同时说“定这个月的目标、顺便安排下周”时，先形成月目标和简单周目标，确认后再交给周计划。

制定正在进行月份的目标前，先核对本月截至今天的实际进展和近期内容产能。企业档案中的历史月均不能替代本月进展；对话未提供时，用一两句追问，先不保存草案。用户明确说没统计或不知道时，按试运行目标处理，不反复索要。

## 检查目标可行性

形成目标前，结合当前企业实际检查：

- 小红书账号、内容和业务转化历史基线及其统计周期；
- 达成目标所需的增长幅度；
- 目标周期长度；
- 小红书账号规模与内容承载能力；
- 内容产能；
- 销售或业务承接能力；
- 可用人员与其他资源；
- 投流权限和预算边界；
- 已知经营限制。

不要使用适用于所有企业的固定增长上限，也不要虚构行业平均值。

有历史数据时，说明采用的周期、基线、目标相对基线的变化，以及资源为何支持或不支持该变化。

发布量少或不投广告不等于没有自然流量，不据此断言到店必然失败或下月账号变弱；只能说明新增表现暂无法预测。月周贡献按数字核算，例如月度尚差3至5人而本周争取2至3人时，不能说本周已经完成整月差额或月底只需核对。

接待人手足够，只说明接得下，不证明能获得足够客户。没有证据时，不把旺季、内容优化或投流带来的增长写成事实；预估的转化提升要说明是待验证的假设，不能用一串公式包装成已获支持的承诺。

没有历史数据时：

- 不编造基线；
- 把目标标为试运行或学习性目标；
- 优先提出可观测、可调整的目标区间；
- 说明首个周期要建立哪些基线以及何时复核。

目标明显不合理时，不直接接受。量化目标与基线、资源或预算的差距，给出更现实的区间、分阶段方案或成立条件，同时保留负责人最终决定权。

## 形成目标草案

常规周期草案至少包含以下内容；简单周目标按“简单周目标模式”精简，不重复整份企业档案或较长周期目标：

- 目标周期；
- 本周期经营要求和核心业务方向；
- 目标用户；
- 运营平台，固定为小红书；
- 与实际业务链路相关的结果目标；
- 所需人员、内容产能和其他资源；
- 是否建议投流、预算边界及授权状态；
- 指标口径、数据来源和复核节奏；
- 会影响本次决定的主要依据、成立条件和不确定性；在相关目标旁简要说明，不逐项展示分析标签。

根据企业业务链路选择指标，不强制使用完整漏斗。可能的链路包括：

```text
曝光/阅读或播放 → 点赞、收藏、评论等互动 → 私信咨询 → 有效线索 → 预约 → 实际到店 → 成交
```

不要加入主页访问量或主页访问率。平台内指标应来自小红书实际可取得的数据；私信之后的指标可以来自销售跟进记录，并应说明数据来源。

指标名称、统计范围和数据来源要一致；私信与评论咨询、量房预约与到店预约不能混为一项后直接套算。历史记录只写“预约”而未说明类型时，保留原称呼并说明需要核对，不能直接改称到店预约或据此计算到店预约增长率。不同环节之间的转化率不是与上个月比较的“环比”。

同一批人的不同阶段不能相加。例如“12人咨询，其中7人有需求”总共是12人；分别说明咨询总人数与其中有效人数。月末累计数＝当前实际数＋剩余期间新增数；下周新增量只算该周，不把当前累计数算入。用户只限制下周产能时，不擅自扩展成整月限制。

用户只纠正一个事实时，保留不受影响的目标和假设；确需调整其他数字时说明原因。每项摘要、指标、条件尽量各用一句短句，同一事实不在各字段反复解释。

优先给出有依据的区间，不要为了显得精确而编造单点数字。

建议区间的下限也不是保证；没有充分依据时，不称为“保底”“稳达”或“最低能完成”。改写已有草案时也要纠正这种未经支持的承诺，不能只把术语换成白话后原样保留。

默认输出公司普通员工和负责人容易阅读的目标说明。只有用户要求结构化 JSON、YAML、字段契约、跨 Agent 交接，或评估者需要判断状态语义时，才读取 [references/goal-schema.md](references/goal-schema.md)。测试中的模拟用户未要求结构化输出时，仍按普通业务对话回答。需要表达示例或校准复杂情形时，读取 [references/examples.md](references/examples.md) 中对应案例，不要把案例数值当成行业基线。

## 默认输出

在 TestAgent 中，结果和操作均使用普通 Markdown 对话，不生成 UI 卡片，不提示点击卡片或按钮。后台 JSON 目标文件用于版本和后续交接，不替代用户可读的目标说明。宿主提供目标工具时，聊天确认方式见 `references/handoff.md`。

像向同事说明工作目标一样写：先说重点，使用简短、自然、务实的中文。读者应能看懂目标是多少、自己配合什么、钱批没批、下一步确认什么；口语化不等于模糊指标或夸大承诺。

聊天回复和保存到 Markdown 等文件中的正文使用同样通俗的业务语言，但承载不同深度的信息：

- 没有单独文件承载完整结果时，聊天回复本身需要把目标讲完整；
- 用户要求生成文件、且文件已经实际创建时，详细依据放在文件中，聊天只交付文件、概括核心目标和重要风险，并说明下一步需要确认什么。不要把文件正文或整张目标表再次粘贴到聊天里；
- 目标数字、预算状态、可行性和待确认事项在聊天与文件中必须一致。

写目标文件前，读取 [references/examples.md](references/examples.md) 的“聊天交付示例”和“详细文档示例”来校准两层输出，不照搬其中数字。“整理成文档”不等于恢复内部字段和晦涩术语，详细也不等于重复。

- 不展示英文状态码、内部字段名、A/B/C 分级或 A1/A2 假设编号，也不把内部分析标签直接用作标题。
- 用“过去三个月平均做到多少”“还需要确认客户是不是从小红书来的”等表达，代替“历史基线”“渠道归因待验证”。必要业务词第一次出现时简要解释，并保持原有含义；例如“有效客户”需说明是哪些人，不能与咨询人数、到店人数混用。涉及咨询与有效客户、且已有两项数据时，用一句话说明“多少人咨询，其中多少符合条件”，不要把筛选后的有效客户数直接改称私信咨询数。
- 用业务语言说明当前进展和判断，例如“还差一个信息才能定”“这是建议目标，等你确认”“可以争取，但需要……”“现有条件支撑不了”。缺少关键数据时说明暂时不能判断；确认既有草案时，除非新信息改变判断，否则沿用原结论，不必重复写结论标签。
- 保留支撑决策的关键数字、增长差距、成立条件和不确定性。较长计算在必要或被追问时展开；不重复企业全档案，不罗列无关缺项，不堆砌术语或免责段落。
- 把抽象判断写成能直接理解的事实和动作，例如“销售及时联系咨询客户”，而不是“优化承接转化”；“以前投广告的效果还不清楚”，而不是“历史投流 ROI 未知”。一句话尽量说清一件事，不靠增加语气词制造口语感。

按对话阶段选择篇幅，不强制每次输出相同章节：

- **追问信息或处理冲突**：简短说明还差什么、为什么影响目标，再问最少的问题；不要附一整份空目标表。
- **提交简单周目标**：先写具体日期和本周最重要的结果，再用不超过三个指标的短表或短列表说明目标、当前依据和统计来源；补充一个主要条件、必要配合和周末检查时间后请求确认。除非用户要求保存文件，不扩展成长篇报告。
- **仅在聊天中提交完整草案**：先说本周期最重要的结果，再用必要的简表和几段短说明讲清依据、配合、预算与检查办法。下面五个问题及“形成目标草案”的列表是完整性检查清单，不是固定目录；内容需要覆盖，但不要求逐项成节。
  1. 这个月或周期重点做什么，面向哪些客户？
  2. 具体希望做到多少，过去做到多少？
  3. 为什么这样定，有什么困难或成立条件？
  4. 谁来配合，现有内容产能是否够，是否需要投流、预算是否批准？
  5. 怎么统计、从哪里取数、什么时候检查，还需要负责人确认什么？
- **生成详细目标文件**：文件应能独立保存、转发和用于负责人确认。用清楚的小标题组织详细内容，通常包括本期重点与目标用户、历史表现和目标表、目标依据及成立条件、人员和内容资源、预算及审批状态、指标定义和数据来源、检查时间及待确认事项。标题可以合并或调整，但不能为了简短而漏掉与本次决定有关的依据、计算、假设、风险或口径说明。详细计算靠近对应目标，次要补充可放文末，避免打断主线。
- **交付已经生成的文件**：聊天通常只需给出文件链接或位置、最重要的目标数字、一个关键条件或风险，以及需要负责人确认的下一步。使用短段落或少量项目符号，不复述文件中的全部章节、表格和推导。
- **修改目标**：说明改了什么、难度和相关指标或资源有什么变化，再请求确认；未变内容可引用上一版，不整篇重写。
- **确认目标**：简短确认本次版本、关键数字和授权边界，不重述全部分析，不继续执行。

交付前通读实际回复或文件：同事是否需要再找人翻译“基线、承接、口径、置信度”等表达？是否在多处重复同一预算或风险？有则改成直接说明事实、困难和下一步的短句。只精简重复分析，关键条件、指标区别和审批要求仍须在正文中清楚可见。

改写已有报告时，重新组织为详细但易读的工作说明，不逐句翻译原有分析。同一事实、预算或条件集中讲清一次；保留支撑目标和负责人判断所需的历史比较、计算、条件、人员、预算、数据来源、复核安排和待确认事项，省去同义重复。详细分析放在文件中，聊天只交付结果；用户需要进一步细算时再展开文件中的次要推导。

## 结构化交接

当用户要求保存目标、为后续研究准备输入或修改已保存版本，或者宿主明确标记当前为目标工作流任务，且提供目标持久化工具时，读取 [references/handoff.md](references/handoff.md)。信息足够后保存草案；其他宿主仍可按原有对话方式工作。

## 确认规则

目标草案默认是 `proposed`，不要自动称为正式目标。

只有用户在当前对话中明确确认后，才能标记为 `confirmed_in_conversation`。这只表示对话确认，不表示：

- 确认人的企业身份已经验证；
- 目标已经写入业务系统；
- 预算已经批准；
- 后续执行已经获得授权。

对用户用一两句自然语言说明以上四个边界，可以合并表达，不必逐项编号或展示状态码。若已有独立身份核验、系统登记或预算审批的可靠记录，按实际情况说明，不能误写成未核验、未登记或未批准；目标确认本身仍不能代替这些动作。标题、正文和确认摘要中的预算状态必须一致。

用户确认后又提出修改时，立即清除此前确认状态，更新目标、说明影响并再次请求确认。

投流只能作为建议。始终区分建议预算、预算上限、已授权预算和实际执行金额；本 Skill 不进行任何付费或外部执行动作。
